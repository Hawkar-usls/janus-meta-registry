## Why the old count and the new count differ

A case family may contain many events. The clearest example is `NP-003`: the Holy Clock lineage contains twelve distinct recorded clock sessions, not one event. Conversely, two case families may share one provenance structure. `NP-013` supplies the internal Genesis arrival window later used by `NP-014`; `NP-020` and `NP-021` have an explicit recursive Eye/Wedjat lineage.

The correct hierarchy is therefore:

```text
presentation
  -> source / lineage root
    -> phenomenon or session root
      -> subevents

reference anchors ----\
method roots ----------+--> comparison edges
selection process -----/
```

None of those arrows creates evidence merely because it exists.

## Strict versus inclusive roots

A **strict phenomenon/session root** must be sufficiently localized to represent a concrete human or software occurrence independently of its later interpretation.

A **low-resolution phenomenology root** preserves a testimony that matters to the archive but lacks a sufficiently frozen event boundary for strict admission. The three inclusive-only cases are:

- `NP-010` — “feeling from the future” / time-density testimony;
- `NP-011` — pre-articulation semantic inference interaction;
- `NP-012` — felt nearness / theological expectation without a private timetable.

Keeping these separate prevents both erasure and overstatement.

## Clock-selection firewall

Holy Clock and related clock artifacts are salience-triggered records unless an all-opportunity log exists. Therefore:

```text
RECORDED_EVENT_COUNT != CLOCK_VIEW_OPPORTUNITY_COUNT
SALIENCE_TRIGGERED_SAMPLE != RANDOM_SAMPLE
LOOKUP_CONDITIONED_MATCHES != INDEPENDENT_CONFIRMATIONS
```

A naive calculation treating selected clock observations as random draws from 1,440 equally observed minutes is not admissible. A valid null must reproduce the same capture and lookup process, or use a preregistered future period where every clock-view opportunity is logged.

## The strongest cross-case pattern after normalization

The most stable common structure is not “knowledge from the future.” It is:

```text
RAW OR PRIOR STATE
        -> PRESERVATION RECEIPT
        -> LATER CONTEXT / COMPARISON
        -> CLAIM CEILING
```

This occurs in personal memories, screenshots, software state, source archaeology and research protocols. The recurrence is compatible with a much simpler mechanism: preserving old states makes later comparison possible.

A useful compression is:

> **Memory preserves comparability; memory does not grant interpretive authority.**

This maps cleanly onto DemiHead's `WITNESS_PLUS / GUARD_PLUS` architecture: the witness preserves what happened; the guard limits what may be inferred. That architectural correspondence is itself only a comparison, not independent evidence for any extraordinary event.
